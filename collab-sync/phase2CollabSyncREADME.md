# collab-sync — Phase 2

Real WebSocket transport, IndexedDB-backed offline queue, role-based access control, and server-side op log with replay-on-reconnect — on top of the Phase 1 `crdt-engine`.

---

## What this is

Phase 1 (`crdt-engine`) proved the CRDT algorithms converge under arbitrary delivery orders, partitions, and concurrent edits — using an in-memory simulator. Phase 2 replaces the simulator with real network transport: a Node.js relay server forwards operations between clients over WebSockets, the relay maintains an op log so reconnecting clients can be brought up to date, and clients persist locally-generated operations to IndexedDB so they survive offline periods.

The CRDT layer is unchanged. `Replica` from Phase 1 is wrapped by `ClientSync` which translates between local operations and wire messages.

---

## Architecture

```
shared/
  protocol.ts         Wire message types (OpMessage, MetaMessage, JoinMessage, ...)
  roles.ts            Role enum + permission checks + HMAC token mint/validate

src/server/
  RelayServer.ts      WebSocket server — forwards ops, enforces roles, replays log
  SessionManager.ts   Token mint/validate, site registry
  server.ts           Entry point: starts relay on configured port

src/client/
  ClientSync.ts       Wraps Replica: connects socket, wires send/receive, fires events
  ConnectionManager.ts WebSocket lifecycle + exponential backoff reconnect
  OfflineQueue.ts     IndexedDB-backed op queue for offline editing
  cli.ts              Interactive client REPL for live demos
```

---

## How Phase 2 builds on Phase 1

| Phase 1 export        | Phase 2 consumer                                  |
|-----------------------|---------------------------------------------------|
| `Replica`             | `ClientSync` wraps it; never modified             |
| `Replica.insert()` / `delete()` | Called by editor/CLI on user input        |
| `Replica.receive()`   | Called by `ClientSync` on incoming `OpMessage`    |
| `Replica.drainOutbox()` | Called by `ClientSync` send loop                |
| `CausalBuffer` (inside `Replica`) | Tolerates duplicates and out-of-order delivery — essential for relay log replay |
| `LWWRegister.snapshot()` / `merge()` | LWW state shipped via `MetaMessage` |

The Phase 1 clock-sequencing invariant (snapshot before increment) is preserved end-to-end. The relay never inspects op semantics — it only reads `op.clock` to identify which clients have already seen each op, then forwards `WireMessage`s unchanged.

---

## Sync-on-reconnection

The relay maintains an append-only op log of every forwarded operation. When a client joins or rejoins, it sends its current vector clock in the `JoinMessage`. The relay walks the log and re-sends every op the client has not yet seen, in log order, before broadcasting the join to other peers.

This closes the loop on the proposal's "offline editing with sync-on-reconnection" requirement: ops generated while a client was offline are flushed by the client (outbound direction, via `OfflineQueue`), AND ops generated by other clients while this one was offline are replayed by the relay (inbound direction, via the op log).

The log is bounded at 10,000 ops to prevent unbounded memory growth; clients offline for longer than that may miss some ops. For typical session lengths and offline windows this bound is generous (≈15 minutes of constant typing).

- `fake-indexeddb` — in-memory IndexedDB used by the **test suite only**


The `-r tsconfig-paths/register` flag makes ts-node resolve `import { Replica } from "crdt-engine/src/simulator/Replica"` correctly without ugly `../../../crdt-engine/src/...` relative paths. Tests use Jest's separate `moduleNameMapper` configuration which is already in place.

## Running on a single machine

The simplest case for development. One relay process plus one or more client processes, all on the same machine, communicating over `localhost`.

### 1. Start the relay

```bash
PORT=8787 npm run server
```

The relay prints the owner site ID and owner token at startup. The output looks like:

```
  Owner Site ID : 72d91de1-e41b-455f-94ef-ffbe58241663
  Owner Token   : eyJ...
```

Copy both values.

Note: `server.ts` reads the port from the `PORT` environment variable, not from `--port`. The session secret is generated automatically by `SessionManager`.

### 2. Connect the owner client

The `--site` flag **must exactly match the siteId encoded in the token**. Use the `Owner Site ID` printed by the server:

```bash
npm run client -- --site <owner-site-id> --token <owner-token> --db-dir /tmp/collab-owner
```

> **`--db-dir` is required when running multiple clients on the same machine.** `node-indexeddb` holds an exclusive file lock on its database directory. Two client processes in the same working directory will conflict. Give each client a unique directory.

Each client opens an interactive REPL — type `help` to see all commands. After the REPL loads, run `connect` to join the session:

```
<owner-site-id>> connect
```

### 3. Mint a token for a second client

In the **owner** REPL, use the `mint` command:

```
<owner-site-id>> mint bob editor
  minted token for bob (editor):
  --site bob --token eyJ...
```

Copy the values. Then in a **new terminal**:

```bash
npm run client -- --site bob --token <editor-token> --db-dir /tmp/collab-bob
```

After the REPL loads, run `connect` in bob's terminal:

```
bob> connect
```

The `--site` value **must exactly match** the siteId you passed to `mint`.

## Running across two devices on a LAN

The relay binds to all network interfaces by default, so any device on the same LAN can reach it once you know the host's IP address.

### 1. On the host device — find its LAN IP

**Linux / macOS:**
```bash
ip addr show | grep "inet " | grep -v 127.0.0.1
hostname -I
```

**Windows:**
```cmd
ipconfig
```

Look for an address like `192.168.1.x` or `10.0.0.x`. Save this — call it `<HOST_IP>` below.

### 2. On the host device — start the relay

```bash
PORT=8787 npm run server
```

### 3. Open the firewall on port 8787

**Linux (ufw):**
```bash
sudo ufw allow 8787/tcp
```

**Linux (firewalld):**
```bash
sudo firewall-cmd --add-port=8787/tcp --permanent
sudo firewall-cmd --reload
```

**macOS:** System Settings → Network → Firewall → allow incoming for the `node` process.

**Windows:** Windows Defender Firewall → Inbound Rules → New Rule → Port → TCP 8787 → Allow.

### 4. On the second device — connect

In the host's owner REPL: `mint bob editor`. Then on the second device:

```bash
npm run client -- --site bob --token <editor-token> --url ws://<HOST_IP>:8787
```

After the REPL loads:

```
bob> connect
```

### 5. Verify connectivity

In each client REPL:
```
<owner-site-id>> connect
<owner-site-id>> state
```
```
bob> connect
bob> state
```

The state line should show `[connected]`. If `[reconnecting]` repeats:

- **Wrong IP** — re-check `<HOST_IP>` on the host
- **Firewall** — verify with `nc -zv <HOST_IP> 8787` from the second device
- **Different networks** — the devices must be on the same LAN
- **Token expired or wrong** — restart the relay and use new tokens

## Demo scenarios

> **Note on prompts:** The REPL prompt shows the full `--site` value you passed on the command line. `owner>` below represents the owner client whose actual prompt is the generated UUID (`<owner-site-id>>`). `bob>` and `charlie>` are clients whose `--site` you chose when running `mint`.

> **Multi-client on one machine:** pass `--db-dir /tmp/collab-<name>` to give each client its own data directory.

---

**Basic two-client convergence:**
```
owner> connect
bob>   connect
owner> ins 0 hello
bob>   state              ← shows "hello"
bob>   ins 5 -world
owner> state              ← shows "hello-world"
```

---

**Late joiner — replay on join:**
```
owner> connect
owner> ins 0 hello
owner> ins 5 -world
bob>   connect            ← bob joins AFTER owner's edits
                          ← relay replays the missed ops automatically
bob>   state              ← shows "hello-world"
```

The relay log replay closes the gap where late joiners used to start with empty state.

---

**Offline edit on one side, then reconnect:**
```
owner> connect
bob>   connect
owner> ins 0 hello
bob>   state             ← "hello"
owner> offline           ← simulates network drop
owner> ins 5 -world      ← queued in IndexedDB, not yet sent
owner> queue             ← shows queue size > 0
owner> online            ← reconnects and flushes queue
bob>   state             ← sees owner's offline edits
```

---

**Bidirectional offline editing — both sides sync on reconnect:**
```
owner> connect
bob>   connect
owner> ins 0 hello
bob>   state             ← "hello"
owner> offline           ← owner goes dark
owner> ins 5 -alice      ← queued locally, not sent
bob>   ins 5 -bob        ← bob keeps editing live; owner doesn't see this
owner> online            ← owner reconnects:
                         ←   outbound: queued ops flush to relay → bob receives
                         ←   inbound:  relay replays bob's "-bob" → owner receives
owner> state             ← converged with bob
bob>   state             ← converged with owner
```

---

**Real network drop (cross-device):** disconnect the second device from WiFi, type a few characters in its CLI, reconnect WiFi. `ConnectionManager` exponential-backoff reconnects automatically; `ClientSync` flushes the outbound queue; relay replays missed inbound ops. Both sides converge.

---

**Role enforcement:**
```
owner> connect
charlie> connect          ← charlie was minted as role=viewer
charlie> ins 0 X
  ✗ permission_denied: Role "viewer" cannot insert
```
Other clients are unaffected — the relay rejects without forwarding.

---

**Resetting between demo scenarios (without restarting the relay):**

When you want to start a fresh scenario without restarting the relay (and losing your tokens), the owner can reset the entire session:

```
owner> connect
bob>   connect
owner> ins 0 hello-world
owner> state             ← "hello-world"
bob>   state             ← "hello-world"
owner> reset             ← clears relay log + resets all connected clients
owner> state             ← empty document
bob>   state             ← empty document
                         ← now start a new scenario from scratch
owner> ins 0 fresh-start
```

`reset` is Owner-only. All currently connected clients are reset simultaneously. Clients that are disconnected when `reset` runs will start with an empty document when they reconnect (the relay log is empty, so no ops replay).

## Edit scenarios and edge cases

### CRDT correctness

**Delete to empty and re-insert (single-client):**
```
owner> connect
owner> ins 0 hello
owner> del 4
owner> del 3
owner> del 2
owner> del 1
owner> del 0
owner> state           ← empty
owner> ins 0 fresh
owner> state           ← "fresh"
```

**Delete to empty and re-insert (two-client):**

With the relay log, this works regardless of join order. Bob can connect before or after the owner's edits — the log replay ensures bob ends up converged.
```
owner> connect
bob>   connect
owner> ins 0 hello
owner> del 4
owner> del 3
owner> ins 3 LP
bob>   state            ← converged with owner
```

**Delete with concurrent inserts (two-client):**
```
owner> connect
bob>   connect
owner> ins 0 hello
bob>   state            ← "hello"
owner> del 4            ← owner deletes 'o'
bob>   ins 5 !          ← bob inserts at same time
owner> state            ← both ops applied, converged
bob>   state            ← same result as owner
```

The RGA delete targets a specific node by identity, not by offset, so concurrent inserts and deletes at the same position converge deterministically on both clients.

### Offline queue

**Reconnect mid-flush:** Disconnect network during `online` flush. Ops sent before the drop are cleared from the queue; the rest remain and will be sent on the next reconnect. No op is duplicated or lost.

**Queue inspection while offline:**
```
owner> offline
owner> ins 0 a
owner> ins 1 b
owner> ins 2 c
owner> queue           ← shows 3
owner> online          ← flushes all 3
owner> queue           ← shows 0
```

### Boundary conditions

**Delete on empty document:**
```
owner> del 0           ← prints "nothing at offset 0"
```

**Insert past document length:** the RGA clamps to the end of the list — no crash, op appends.

**Insert empty string:** inserting zero characters is a no-op; no op is generated or sent.

### Expected failures

| Scenario | Expected outcome |
|---|---|
| Stale token (relay restarted) | `connect failed: invalid_token: Token validation failed` |
| Wrong `--site` for token | `connect failed: invalid_token: Token siteId does not match...` |
| `mint` before connecting | `mint failed: mintToken: not connected` |
| `reset` before connecting | `reset failed: reset: not connected` |
| Editor running `reset` | `permission_denied: Role "editor" cannot reset the session log` |
| Editor minting token | `permission_denied: Role "editor" cannot mint tokens` |
| Viewer inserting/deleting | `permission_denied: Role "viewer" cannot insert/delete` |
| Two clients same dir, no `--db-dir` | Second client crashes with `Database is not open`. Pass `--db-dir`. |

## Wire protocol summary

All messages are JSON over WebSocket. See `shared/protocol.ts` for full type definitions.

**Client → Relay**
- `JoinMessage` — first message after socket open. Carries siteId, token, current vector clock.
- `OpMessage` — single RGA insert or delete operation.
- `MetaMessage` — full LWW state snapshot.
- `MintTokenRequest` — Owner-only request to issue a token for a new site.
- `ClearLogRequest` — Owner-only request to wipe the relay's op log and reset all clients.

**Relay → Client**
- `WelcomeMessage` — sent after successful join. Includes assigned siteId, role, list of currently active sites.
- `OpMessage` — forwarded from another client OR replayed from the op log.
- `MetaMessage` — forwarded from another client.
- `SiteJoinedMessage` / `SiteLeftMessage` — presence updates.
- `TokenMintedResponse` — reply to a successful mint request.
- `LogClearedMessage` — broadcast to all connected clients after the op log is cleared. Each client resets its local Replica and offline queue on receipt.
- `ErrorMessage` — fatal or non-fatal error.

The replay path uses the same `OpMessage` shape as live forwarding, so the client doesn't need to distinguish the two — it just feeds them all to `Replica.receive()`.

---

## Tokens and access control

Tokens are `base64url(payload).base64url(hmac-sha256-signature)`. Payload is JSON containing `{ siteId, role, sessionId, expiresAt }`. The relay holds the signing secret; clients hold opaque tokens.

Three roles defined in `shared/roles.ts`:
- `Owner` — can insert, delete, change roles, mint tokens, reset the session log
- `Editor` — can insert, delete; cannot manage roles
- `Viewer` — read-only

Permission checks fire on every incoming `OpMessage` and privileged request at the relay. Rejected messages produce a non-fatal `ErrorMessage` to the sender; the message is not forwarded to anyone else and is not appended to the log.

## Design notes

**Offline queue ordering.** Ops are enqueued in the order `Replica` generates them. Because `Replica` increments its clock before placing each op in the outbox, enqueue order equals causal order for that site. The IndexedDB `seqNo` autoincrement key preserves this on `getAll()`. No sort needed on flush.

**Op log replay.** On every `JoinMessage` the relay walks its log and re-sends ops the client has not yet seen, identified by comparing `joinMsg.clockSnapshot[sender]` to `entry.clock[sender]`. Replays use the same `OpMessage` envelope as live forwarding. The client's `CausalBuffer` deduplicates and orders correctly even if a replay overlaps with new live ops.

**Own-op replay on fresh restart.** The relay does not unconditionally skip a rejoining client's own ops. After a process restart the client has a fresh Replica (clock `{}`), so it needs its own previous ops replayed to reconstruct the document. For a normal reconnect the client's non-empty clock causes its own ops to be correctly skipped.

**Bounded log retention.** The log is capped at 10,000 entries. When full, the oldest entry is dropped. Clients offline longer than the retention window may miss some ops. A future enhancement is periodic state snapshots that clients can download as a starting point, after which the log replay covers everything since the snapshot.

**Partial flush resilience.** `flushQueue` in `ClientSync` calls `clearUpTo(seqNo)` after each successful send, so if the socket dies mid-flush, remaining ops stay in IndexedDB and are picked up on the next reconnect. No op is delivered twice; no op is lost.

**Session reset.** The `ClearLogRequest` / `LogClearedMessage` round-trip lets an Owner wipe the relay's op log and reset all connected clients atomically from within the REPL. This avoids having to restart the relay (which invalidates all tokens) just to start a new demo scenario.

**IndexedDB in Node.js.** The CLI uses `node-indexeddb`, a LevelDB-backed IndexedDB. Queued ops are written to an `indexeddb/` directory in the working directory and persist across CLI restarts. Phase 3's browser deployment will use native browser IndexedDB. Tests use `fake-indexeddb` (pure in-memory).

**Reconnect with same siteId.** If a client with siteId X reconnects while the relay still considers X connected (e.g. its old socket hasn't timed out), the relay closes the old session and accepts the new one. This avoids a deadlock where the client can't reconnect because its old siteId is "taken" by a zombie session.

## What Phase 2 does not include

Deferred to Phase 3:

- CodeMirror 6 editor integration (the visible UI)
- Cursor presence and remote selection rendering
- Local undo/redo via compensating ops
- Periodic document-state snapshots to extend the effective replay window past the log retention bound
- mDNS service discovery (currently manual IP entry)
- TLS — current setup is plain `ws://`, fine for trusted LAN demos but not for production over the internet

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `Missing script: "server"` | `server`/`client` entries missing from `package.json`; see Setup |
| `Cannot find module 'crdt-engine/src/...'` | `tsconfig-paths` not installed or `-r tsconfig-paths/register` missing |
| `OfflineQueue: no IndexedDB implementation available` | `node-indexeddb` not installed; run `npm install node-indexeddb` |
| `Error: Database not loaded yet` | `node-indexeddb/auto` imported before `dbManager.loadCache()` was awaited |
| `ModuleError: Database is not open` (second client on same machine) | Two clients in same directory locking each other out; pass `--db-dir /tmp/collab-<site>` |
| Client stuck in `[reconnecting]` | Wrong IP, firewall, or different networks |
| `connect failed: invalid_token` | Token from old relay run, or `--site` mismatches token siteId |
| Inserts work but other client doesn't see them | Other client also needs to run `connect` and show `[connected]` |
| Works on `localhost` but not LAN | Firewall on host device |
| Owner sees empty state after relay restart | Relay log was cleared on restart; reconnect and the relay replays your own previous ops |
| Bob shows stale content from a previous run | Bob's offline queue has ops from the old session; owner should run `reset` before starting a new scenario |

To verify raw network connectivity:
```bash
nc -zv <HOST_IP> 8787
```
